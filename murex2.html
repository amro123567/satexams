Symbolic mode (relative changes)

chmod u+x run.sh          # add execute for owner
chmod go-rwx file1.txt    # remove ALL rights from group and others; owner unchanged
chmod a+r file            # everyone can read (a = ugo)
chmod ugo+r f && chmod go-wx f && chmod u+wx f   # ends as rwxr--r-- = 744
chmod u=rwx,g=rx,o= f     # "=" sets exactly → 750
chmod -R 755 /data        # -R = recursive (dir + contents)
Numeric mode sets all bits absolutely; symbolic +/- changes only what you name. chmod 700 f does not change the owner to “user 700” — it’s rwx for owner only. “Exclusively the owner” → 700.

3systemd, services & system information

How Linux starts and manages services (systemd/systemctl), how to read service logs (journalctl), and every command for “tell me about this machine”, with what each output field means.

What systemd is

  • systemd is the init system on almost every modern Linux (RHEL/CentOS/Rocky, Ubuntu, Debian, SUSE). It is PID 1: the first process the kernel starts, and the parent/adopter of all others.
  • It starts services at boot (in parallel, respecting dependencies), supervises them (restarts on crash), collects their logs (journald), and handles timers, mounts, sockets, hostname, time and logins.
  • Everything it manages is a unit, described by a unit file. You control it with systemctl and read its logs with journalctl.
  • Older systems used SysV init (/etc/init.d/ scripts, service, chkconfig, runlevels). You may still see those commands; on systemd they are redirected to systemctl.

Troubleshooting a service that won’t start

  1. systemctl status app: read Loaded (right file? enabled?) and Active (Result: exit-code / signal / timeout).
  2. journalctl -xeu app: find the real error (stack trace, “permission denied”, “address already in use”, “no such file”).
  3. Check the usual causes:
    • Port in use: ss -tlnp | grep :8080.
    • Wrong path or not executable: ls -l on the ExecStart binary, chmod +x.
    • Permissions for the User=: sudo -u murex ls /opt/murex.
    • Bad config syntax (nginx -t, sshd -t).
    • Missing environment variables (systemd doesn’t read your .bashrc).
    • A dependency down.
    • Disk full: df -h.
    • SELinux: ausearch -m avc.
  4. Run the ExecStart command by hand as that user to see the error directly.
  5. After fixing the unit file: daemon-reload → reset-failed → restart → status.

How Git actually stores your work

  • .git/ holds the whole repository. Delete it and the folder is no longer a repo; the files stay.
  • Four object types, each named by a SHA-1 hash of its content: blob (file content), tree (a directory: names → blobs/trees), commit (a tree snapshot + parent commit(s) + author + message), tag (annotated tag). Same content = same hash, so Git stores each version once.
  • A commit is a full snapshot, not a diff. Diffs are computed when you ask.
  • A branch is just a file (.git/refs/heads/main) containing one commit hash. Creating a branch is instant and costs 41 bytes. Committing moves the current branch forward.
  • HEAD (.git/HEAD) normally contains ref: refs/heads/main, i.e. which branch you’re on. Detached HEAD = HEAD contains a commit hash directly (after git checkout <sha> or a tag).
  • Remote-tracking branches (origin/main) are your local memory of where the remote’s branches were at the last fetch. You can’t commit on them.

Trace drills (exam style), with answers

Method: keep a small table of branch → commit → file content, plus index and working dir. Update it after each command. Ask: is the file tracked? staged? committed? on which branch?

Drill 1: branch without switching

git init; echo A > f; git add f; git commit -m c1     # master: c1 (f=A)
git branch dev                                         # dev → c1, still on master
echo B >> f; git commit -am c2                         # master: c2 (f=A,B); dev still c1
git switch dev; cat f

Answer: A. dev was created at c1, and c2 was committed on master.

Drill 2: commit -a and new files

echo x > new.txt            # untracked
echo y >> f                 # tracked, modified
git commit -am "update"

Answer: only f is committed; new.txt stays untracked (??). -a stages tracked files only. If new.txt were the only change: “nothing added to commit but untracked files present”.

Drill 3: uncommitted changes travel across branches

# master and dev both at c1 (f=A), working dir clean
echo B >> f                 # modify, don't commit
git switch dev; cat f

Answer: A B. f is identical in both branch snapshots, so Git keeps your modification in the working dir. If f differed between master and dev, the switch would be refused (“local changes would be overwritten”).

Drill 4: a file committed only on one branch

git switch -c feat
echo hi > feat.txt; git add feat.txt; git commit -m feat
git switch master; ls

Answer: feat.txt is gone from the working dir (master’s snapshot doesn’t have it). Switching back to feat brings it back.

Drill 5: the three resets

# commits: c1 (f=1) → c2 (f=2) → c3 (f=3), HEAD at c3, clean
git reset --soft  HEAD~2   # HEAD=c1 · index f=3 · working f=3 · status: f staged (modified)
git reset --mixed HEAD~2   # HEAD=c1 · index f=1 · working f=3 · status: f modified, not staged
git reset --hard  HEAD~2   # HEAD=c1 · index f=1 · working f=1 · status: clean; c2, c3 only in reflog

Drill 6: revert vs reset

# c1 (f=1) → c2 (f=2)
git revert HEAD

Answer: a new commit c3 is created with f=1. git log --oneline shows 3 commits (c3 “Revert …”, c2, c1). With reset --hard HEAD~1 instead, the log would show only c1.

Drill 7: fast-forward or not?

# main at c1; feature has c2, c3 on top of c1
git switch main; git merge feature        # → "Fast-forward": main = c3, no merge commit
# if main had its own commit c4 first → merge commit M(c4, c3); log --graph shows a diamond

Drill 8: stash round-trip

echo change >> f; git stash; cat f       # original content (working dir clean)
git stash list                            # stash@{0}: WIP on main: …
git stash pop; cat f                      # "change" is back; stash list empty

Drill 9: delete an unmerged branch

git switch -c exp; echo t > t; git add t; git commit -m t
git switch main
git branch -d exp      # error: The branch 'exp' is not fully merged
git branch -D exp      # deleted (commit only reachable via reflog now)
git branch -D main     # error if you're on main: cannot delete the branch you are on

Drill 10: the 2026 paper’s trap

mkdir murex_test
git init murex_test               # repo created INSIDE murex_test, you're still outside it
git checkout -b murex             # as written → "not a git repository" (assume cd murex_test for the rest)
echo "MUREX ROCKS" > mymurexfile   # untracked
touch mymurexfile                 # only updates the timestamp
git commit -am "..."              # nothing committed: the file is untracked; no commits exist yet
git add mymurexfile               # staged (line 1)
echo "MUREX ALWAYS ROCKS" >> mymurexfile   # working dir has 2 lines, index has 1
git branch                        # prints nothing (unborn branch)
git diff murex master             # error: unknown revision
git push origin master            # error: no remote / src refspec master does not match any
git branch -D murex               # error: branch 'murex' not found

Answer: the file is in neither branch (no commit was ever made). It exists only in the working dir; only the first line is staged.

Tricks & good practice

  • git log --oneline --graph --all --decorate: alias it (git config --global alias.lg "log --oneline --graph --all --decorate").
  • Always run git diff --staged before committing, and git status before and after anything risky.
  • git add -p to make small, focused commits; git commit --fixup=<sha> + git rebase -i --autosquash to fix older commits cleanly.
  • git switch - toggles between the last two branches.
  • git stash -u when untracked files must be saved too; name your stashes with -m.
  • git push --force-with-lease, never plain --force, and never on main/shared branches.
  • git pull --rebase (or pull.rebase=true) avoids pointless merge commits.
  • git restore --source=<sha> file recovers an old version of one file without moving branches.
  • git reflog before panicking: committed work is almost never truly lost.
  • git clean -n before -f; git reset --hard and git restore destroy uncommitted work for good.
  • Good commit messages: imperative subject ≤ 50 chars (“Fix NPE in trade pricing”), a blank line, then why. Reference the ticket (JIRA-123).
  • Workflows: feature branches + pull requests with code review and CI checks · GitFlow (main = production, develop = integration, feature/*, release/*, hotfix/* merged into both main and develop) · trunk-based (short-lived branches, feature flags).
  • git worktree add ../hotfix release-2.1: a second working directory on another branch, without stashing.
  • git rerere (rerere.enabled=true) remembers how you resolved a conflict and reapplies it.
  • Submodules (git submodule update --init --recursive) embed another repo at a fixed commit.

IPv4 addressing

  • IPv4 = 32 bits, written as 4 octets (0–255): 192.168.1.10. IPv6 = 128 bits, hex: 2001:db8::1.
  • An address has a network part and a host part, split by the subnet mask (e.g. 255.255.255.0 = /24, CIDR notation = number of network bits).
  • Network address = first address, host bits all 0 — identifies the network, not assignable. Broadcast address = last address, host bits all 1. Everything between = usable hosts.
  • Default gateway = router that forwards traffic leaving your subnet. MAC address = 48-bit hardware address (L2). ARP maps IP → MAC on the local network.
  • 127.0.0.1 = loopback / localhost (this machine). 0.0.0.0 = “all interfaces” when a server listens. 169.254.x.x = APIPA (DHCP failed).

  SUM(salary)  OVER (PARTITION BY dept_id) AS dept_total,                 -- aggregate without collapsing rows
  LAG(salary)  OVER (ORDER BY hire_date) AS prev_salary                   -- previous row (LEAD = next)
FROM Employees;

Indexes & performance

  • An index is a separate structure (usually a B-tree) that lets the DB find rows without scanning the whole table (full table scan). Speeds up WHERE, JOIN, ORDER BY on indexed columns.
  • Cost: extra storage, and slower INSERT/UPDATE/DELETE (index must be maintained). Not useful on low-selectivity columns (gender) or tiny tables.
  • Clustered index: defines the physical order of the table rows; only one per table (usually the primary key). Non-clustered: separate structure with pointers to rows; many per table.
  • Unique index: also enforces uniqueness → solves both “slow search” and “duplicate invoice numbers”.
  • Composite index (a, b): helps queries filtering on a or a AND b (leftmost prefix), not b alone.
  • Covering index: contains all columns a query needs. Partitioning: split a huge table by range (e.g. by year) → partition pruning.
  • Index killers: functions on the column (WHERE YEAR(order_date)=2026), leading wildcard (LIKE '%x'), implicit type conversion, OR on different columns.

CREATE UNIQUE INDEX ux_invoice ON Sales(invoice_no);

DBMS theory & scaling

  • DBMS = software to store, organize, query and manage data (its primary function: let users store and retrieve data through queries; also handles security, integrity, concurrency, backup/recovery). RDBMS = relational: tables, rows, keys, SQL (Oracle, MySQL, PostgreSQL, SQL Server). NoSQL = document (MongoDB), key-value (Redis), column (Cassandra), graph (Neo4j) — flexible schema, horizontal scale.
  • OLTP (many small transactions, normalized) vs OLAP (analytics, aggregates, data warehouse, star schema).
  • Benefits of an RDBMS on multiple servers: high availability & failover (no single point of failure) · scalability/load balancing (read replicas, sharding) · performance · disaster recovery (replica in another site) · maintenance without downtime.
  • Replication: copies of data (master–slave/primary–replica, synchronous vs asynchronous). Sharding: split rows across servers by key. Clustering: Oracle RAC — several instances, one DB.
  • CAP theorem: a distributed system can guarantee at most two of Consistency, Availability, Partition tolerance.
  • Backup: full / incremental / differential; point-in-time recovery via logs.
  • SQL injection: user input concatenated into SQL (' OR 1=1 --). Prevent with prepared statements / bind variables.
  • Oracle specifics (Murex runs on Oracle/Sybase/SQL Server): DUAL table, ROWNUM, NVL, SYSDATE, VARCHAR2, MINUS, sequences, v$session, v$sql, EXPLAIN PLAN, AWR reports, ORA- error codes (ORA-00001 unique violated, ORA-00942 table doesn’t exist, ORA-01017 invalid login, ORA-00060 deadlock, ORA-01555 snapshot too old, ORA-12154 TNS can’t resolve service).

  • Constructors: the parent constructor runs first (implicit super() as first line). If the parent has no no-arg constructor, the child must call super(args) or it’s a compile error. Constructors are not inherited.

  • Four pillars: encapsulation (private fields + getters), inheritance, polymorphism, abstraction.
  • equals()/hashCode() contract: equal objects must have equal hash codes (needed for HashMap/HashSet).
  • Casting: upcast implicit (Animal a = new Dog()); downcast explicit, wrong type → ClassCastException; check with instanceof.

Lifecycle & fundamentals

Test design techniques

Equivalence partitioning (EP)

Split inputs into classes the system should treat the same; test one value per class. Age valid 18–60 → 3 partitions: <18 (invalid), 18–60 (valid), >60 (invalid) (+ non-numeric/empty).

Boundary value analysis (BVA)

Bugs hide at edges. For a boundary B test B−1, B, B+1 (3-value) or B−1, B (2-value). Range 18–60 → 17, 18, 19, 59, 60, 61.

Book offer at multiples of 5 up to 20 (5→$25, 10→$40, 15→$50, 20→$60): each price point is a boundary → 4,5,6 · 9,10,11 · 14,15,16 · 19,20,21, plus the lower edge of the domain 0,1 → 0, 1, 4, 5, 6, 9, 10, 11, 14, 15, 16, 19, 20, 21 (the most complete option).

Decision table

Conditions × actions; n binary conditions → 2ⁿ rules. Member (Y/N) × order > $100 (Y/N) → 4 rules.

Others

  • State transition: states + events (e.g. order: New → Paid → Shipped → Delivered; account locked after 3 failures).
  • Use case / scenario testing: main flow + alternate flows.
  • Error guessing: experience-based (empty, null, special characters, very long strings, 0, negative, leap year 29 Feb, time zones).
  • Pairwise: cover every pair of parameter values with few tests.

  • File systems: ext4, XFS (Linux), NTFS (Windows). Inode = file metadata. Windows vs Linux: \ vs /, CRLF vs LF line endings, case-insensitive vs case-sensitive names.

JVM: bytecode, GC, thread vs heap dumps

  • javac A.java → A.class = bytecode, which is portable because every OS/CPU has its own JVM that interprets and JIT-compiles it. (C → native binary, not portable.)
  • Heap generations: Young (Eden + Survivor; frequent minor GC) → Old/Tenured (long-lived objects). A full GC runs when the old generation/heap has no space left for allocation; it is slow and can pause the application (“stop the world”). System.gc() is only a request. An object becomes eligible for GC when nothing references it.
  • Collectors: Serial, Parallel, G1 (default), ZGC/Shenandoah (low pause). Flags: -Xms, -Xmx, -Xlog:gc.
  • Thread dump (jstack PID, kill -3 PID, jcmd PID Thread.print): the state and stack of every thread (RUNNABLE, BLOCKED, WAITING, TIMED_WAITING). Use it for hangs, deadlocks, high CPU. Several threads BLOCKED on the same monitor → deadlock/contention.
  • Heap dump (jmap -dump:format=b,file=h.hprof PID, -XX:+HeapDumpOnOutOfMemoryError): every object in memory and its references. Use it for memory leaks / OutOfMemoryError, analysed with Eclipse MAT or VisualVM.

ISTQB-style testing theory

  • Main goal of a test team: provide information and build enough confidence to decide whether to release. You can never prove the absence of faults.
  • Risk-based prioritisation: when time is short, run the high-impact/high-probability tests first. Setup and teardown steps (open/close DB) are needed by the others; changes that alter nothing (replace a value with the same value) and cosmetic edits come last.
  • Tester skills in agile: product/domain knowledge, being a good team player (collaboration, communication), critical thinking. The Product Owner owns the vision and backlog; the Scrum Master facilitates; the team plans its own work.
  • Agile testing: whole-team quality, testing inside the sprint, test automation pyramid (many unit tests, fewer API tests, fewest UI tests), definition of done, test-first (TDD/BDD/ATDD).
  • Field validation recipe (e.g. alphanumeric username, max 16): valid classes (letters, digits, mix, case), boundaries (0, 1, 15, 16, 17), invalid characters (special, spaces, Unicode, emoji), empty, duplicates/case-sensitivity, injection (SQL, XSS), client- and server-side validation, error messages, copy/paste, browsers/mobile.
  • Test timeout (a scenario exceeds its time limit): performance regression, slow or overloaded environment, hang/deadlock/waiting on a resource, larger data, an unrealistic limit.

Clock angle

minuteAngle = 6 * m                    # 360° / 60 min
hourAngle   = 30 * (h % 12) + 0.5 * m  # 360° / 12 h, plus 0.5° per minute

answer = min(diff, 360 − diff)         # 3:00 → 90,  3:30 → |105 − 180| = 75

Traffic light (two-state machine)

A = GREEN; B = RED
loop forever:
    show(A, B); wait(60 s)
    swap: if A == GREEN then (A, B) = (RED, GREEN) else (A, B) = (GREEN, RED)
# invariant: never both green; optional all-red/yellow interval

Reverse an array in place (no library)

i = 0; j = n − 1
while i < j: swap(a[i], a[j]); i++; j--      # O(n) time, O(1) space
